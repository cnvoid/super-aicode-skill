# digital-worker — 数字员工接入规范

## error 级别硬约束

### 1. API 必须可自动发现

每个后端服务必须对外暴露 OpenAPI 规范文档（Swagger/OpenAPI 3.x），数字员工通过读取该文档自动获知所有可用接口。

端点要求：
- OpenAPI JSON 文档暴露在 `/api/v1/openapi.json`
- Swagger UI 暴露在 `/api/v1/docs`（生产环境可关闭或加访问密码）
- OpenAPI 文档必须与代码实现同步（通过注解/装饰器自动生成，不得手工维护）

OpenAPI 文档中必须包含以下信息：
- 每个接口的请求方法、路径、摘要描述
- 每个参数的名称、类型、必填/可选、默认值、描述
- 每个响应状态码对应的响应体 Schema
- 认证方式说明（securitySchemes 字段）

### 2. 所有接口定义必须包含完整 Schema

每个 API 接口的 OpenAPI 定义必须完整描述以下内容，确保数字员工无需猜测即可构造正确请求：

请求参数规范：
- 每个参数标注 `required: true/false`，必填参数缺省时接口返回 400 并指明缺失字段
- 每个参数标注 `type`（string / integer / number / boolean / array / object）
- 字符串参数注明 `maxLength` 和 `format`（email / uuid / date-time）
- 数值参数注明 `minimum` / `maximum`
- 枚举参数完整列出 `enum` 全集
- 每个参数标注 `description`，用自然语言描述该参数的用途和示例值

响应体 Schema：
- 每个成功响应体的 `data` 字段必须展开到嵌套属性的完整 Schema
- 每个可为 null 的字段标注 `nullable: true`
- 分页响应体明确标注 `list`、`total`、`page`、`pageSize` 四字段类型

### 3. 错误信息必须可指导自动修复

数字员工收到非 2xx 响应后，必须能从错误响应中提取足够信息以自动修正请求。错误响应的 `message` 字段要求：

需包含的信息：
- 具体的错误原因（不是"参数错误"而是"缺少必填参数 userId，类型为 string"）
- 修正建议（不是"订单状态不允许"而是"当前状态为 PAID，仅 PENDING 状态可取消"）
- 涉及的具体字段名称（数字员工可据此定位并修正请求体中的对应字段）

禁止的错误信息：
- 模糊描述："系统错误"、"操作失败"、"参数不合法"
- 暴露内部细节：SQL 语句、堆栈信息、框架版本
- 纯英文技术信息返回给中文用户的接口

### 4. 数字员工必须有独立的身份标识和审计

数字员工的认证和审计必须与人类用户区分：

认证方案：
- 数字员工使用独立的 API Key 认证（请求头 `X-Api-Key` 或 `Authorization: Bearer <apikey>`）
- API Key 由管理员在后台签发，每个数字员工独立分配一个 Key
- API Key 可以限定可访问的接口范围（白名单模式）
- API Key 的权限变更实时生效，不需要数字员工重新登录

审计日志：
- 所有接口操作日志中标注 `operator_type: "agent"` 或 `"human"`
- Agent 操作日志包含 `agent_id`（标识哪个数字员工）和 `trigger_source`（标识触发来源：定时任务 / 用户指令 / 自动巡检）
- 数字员工的操作记录可独立查询和追溯
- 关键操作（删除、修改权限、导出数据）必须有额外的确认机制

### 5. 所有写接口必须幂等

数字员工的请求可能因网络波动而重试，所有 POST/PUT/DELETE 接口必须具备幂等性。

幂等实现方式：
- 客户端在请求头中传入 `X-Idempotency-Key`（UUID 格式）
- 服务端在指定时间窗口内（建议 24 小时）对相同幂等键的请求返回相同结果
- 幂等键有效期后，相同的幂等键视为新请求

错误场景约定：
- 幂等键重复但请求体不一致 → 返回 422，message 标明"幂等键冲突，请求体与首次请求不一致"
- 幂等键的返回结果与首次请求一致 → 返回相同响应（包括相同的时间戳和 ID）

### 6. 必须提供批量操作接口

数字员工处理大量数据时，不得逐条调用单个创建/修改接口。以下场景必须提供对应的批量接口：

- 批量创建：POST `/api/v1/{resource}/batch`，请求体为对象数组，返回每个对象的创建结果（含成功/失败明细）
- 批量修改：PUT `/api/v1/{resource}/batch`，请求体为带 ID 的对象数组
- 批量删除：POST `/api/v1/{resource}/batch-delete`，请求体为 ID 数组，返回删除成功的 ID 列表

全部查询必须支持游标分页：
- 响应体中返回 `nextCursor` 字段，客户端传回作为下次查询的起点
- 游标分页在数据量变化时不出现重复或遗漏

## warn 级别软约束

### 7. 数字员工有独立的速率限制

数字员工的速率限制策略应与人类用户区分，通常比人类更宽松：

- 人类用户：登录 5 次/分钟/账户、API 调用 100 次/分钟
- 数字员工：API 调用 1000 次/分钟、批量操作 50 次/分钟
- 超限返回 429 + `Retry-After` 响应头（精确到秒）
- 速率限制配额可在后台动态调整，不重启服务

### 8. API 版本停用需提前通知

数字员工依赖的 API 版本不可随意停用。版本生命周期：

- 当前稳定版本维护 ≥ 6 个月
- 新版本发布时，旧版本进入弃用期（≥ 30 天）
- 弃用期内的响应头携带 `Deprecation: true` 和 `Sunset: <date>`
- 弃用到期前 7 天每日通过响应头提醒
- 数字员工代码中硬编码的 API 版本号应可配置（环境变量注入）
