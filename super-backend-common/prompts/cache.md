# cache — 缓存策略规范

## error 级别硬约束

### 1. 必须防范缓存穿透

缓存穿透：查询一个数据库中不存在的数据，由于缓存中也没有，每次请求都穿透到数据库。

防范方案：
- 布隆过滤器：将数据库中存在的所有 key 加载到布隆过滤器，查询前先判断 key 是否存在。不存在直接返回空，不访问数据库。
- 空值缓存：对于查询结果为 null 的数据，将空值也写入缓存，设置较短的过期时间（1-5 分钟）。

不得对查询不存在的数据不设防，让所有请求都穿透到数据库。

### 2. 必须防范缓存击穿

缓存击穿：热点数据在缓存过期的瞬间，大量并发请求同时穿透到数据库。

防范方案：
- 互斥锁：缓存未命中时，仅允许一个请求去查询数据库并回写缓存，其余请求等待该锁释放后读取缓存。
- 永不过期 + 异步刷新：热点数据在缓存中设置为永不过期，通过定时任务或消费数据库的 binlog 异步刷新缓存内容。

不得让热点数据在缓存过期时引发数据库瞬时高负载。

### 3. 必须防范缓存雪崩

缓存雪崩：大量缓存在同一时刻集体过期，或缓存服务宕机，导致所有请求直接打到数据库。

防范方案：
- TTL 加随机偏移：缓存过期时间在基础值上增加随机秒数（如基础 5 分钟 + 随机 1-120 秒），避免集中过期。
- 缓存高可用：Redis 使用哨兵模式或集群模式，避免单点故障。
- 多级缓存：本地缓存（Caffeine/内存） + 分布式缓存（Redis）构成两级缓存，Redis 不可用时降级到本地缓存。

### 4. 缓存更新必须选择明确策略

缓存更新策略必须在实现前确定并文档化，不得随意混用：

- Cache Aside：查询时读缓存 → 未命中 → 读数据库 → 写缓存。更新时先写数据库 → 再删缓存。适用于读多写少场景。
- Write Through：更新数据时同步写缓存和数据库。适用于数据一致性要求高的场景。
- Write Behind：更新时先写缓存 → 异步批量写数据库。适用于写频繁且允许短暂不一致的场景。

## warn 级别软约束

- 缓存 Key 的设计包含业务前缀和版本号，支持批量失效和灰度切换
- 缓存预热：应用启动时预加载热点数据到缓存，避免冷启动时的缓存击穿
- 缓存监控：暴露缓存命中率指标，低于 90% 时告警
- 序列化方案选择：根据数据大小和读写频率选择 JSON（通用）、Protobuf（高效）、或 Kryo/MessagePack（二选一）
