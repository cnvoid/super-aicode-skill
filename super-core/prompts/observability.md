# observability — 可观测性规范

## error 级别硬约束

### 1. 必须暴露关键业务指标

每个服务必须暴露以下指标供监控系统采集：

- 请求计数器：按接口、HTTP 方法、状态码分组
- 请求延迟直方图：P50、P95、P99 延迟
- 错误率：按接口和错误类型分组
- 业务指标：订单量、支付成功率、活跃用户数等核心业务指标

指标暴露方式：Prometheus 格式的 /metrics 端点（不经过认证拦截器）。

### 2. 关键操作必须配置告警

以下场景必须配置告警规则，在指标超过阈值时通知运维：

- 服务存活：服务连续 3 次健康检查失败 → P0 告警
- 错误率：5 分钟内错误率 > 5% → P1 告警
- 响应延迟：P95 延迟超过 SLA 目标的 1.5 倍 → P2 告警
- 资源使用：CPU > 80%、内存 > 85%、磁盘 > 90% → P2 告警
- 业务异常：支付成功率 < 99%、消息积压 > 1000 → P1 告警
- 依赖服务：数据库/Redis/MQ 连接失败 → P0 告警

告警必须有明确的处理预案，不得仅发通知而无后续动作。

### 3. 分布式调用必须支持链路追踪

微服务架构中，所有跨进程调用必须传播 trace context，实现端到端的链路追踪。

传播方式：通过 HTTP Header（如 traceparent、X-Trace-Id）或消息队列的元数据头传递 trace-id 和 span-id。

每个外部调用（HTTP、RPC、DB、Cache、MQ）作为单独的 Span 记录，Span 必须包含操作名称、耗时、状态（成功/失败）、关键标签。

## warn 级别软约束

- 使用 OpenTelemetry 作为统一的可观测性数据采集标准，避免绑定特定厂商
- 业务日志、指标、链路追踪三者通过 trace-id 关联，形成完整的故事线
- 告警通知分级：P0 电话 + IM 群通知，P1 IM 群通知，P2 邮件通知
- 定期进行故障演练，验证告警通道的有效性和处理预案的可执行性
