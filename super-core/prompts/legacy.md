# legacy — 存量项目约束

当工作目录包含已有代码（非新建项目）时，以下规则优先级**高于** super-core 其他所有规则。

## error 级别硬约束

### 1. 必须检测并尊重项目现有代码风格

修改已有项目前，必须先分析当前代码库的风格模式，按以下优先级逐项对齐：

**响应格式**（优先级最高）：
- 读取已有 Controller/Handler 文件的返回值结构，确定项目当前使用的响应格式
- 如果旧项目已定义 `Result<T>`、`ApiResponse` 等统一响应类 → 沿用该类，不得引入新的响应格式
- 如果旧项目无统一响应（裸返 data）→ 仅在新创建的接口中使用 `{code, message, data}` 结构，不得修改已有接口的返回格式，直到团队明确确认迁移计划

**错误码规范**：
- 读取已有错误码枚举/常量文件，确定项目的错误码分段规则
- 新增错误码必须在已有分段规则内分配，不得创建新的分段体系
- 如果旧项目已存在 `ErrorCode` 枚举 → 新增错误码追加到对应模块分组末尾
- 如果旧项目未定义错误码体系 → 仅在新文件中创建，不在旧文件中插入

**命名风格**：
- 入乡随俗：项目已存在的命名风格（驼峰/下划线、单数/复数表名、DTO/Schema 后缀）必须沿用
- 不得在新文件中引入与旧项目不一致的命名风格

**异常处理**：
- 如果旧项目已有 `GlobalExceptionHandler` 或类似的全局异常处理器 → 新异常类型必须在该处理器中注册
- 如果旧项目没有全局异常处理 → 不在新模块中单独引入，向用户建议统一改造计划

### 2. 修改范围必须限定

修改已有代码时，改动范围严格限于用户要求的目标区域：

- 修改一个方法 → 只改该方法，不得重构整个类
- 修复一个 bug → 只改 bug 相关行，不得顺手重构相邻代码
- 新增一个接口 → 新增对应的 Controller 方法，不得为了统一风格而修改已有接口

以下行为明确禁止：
- 因 skill 规则要求而大规模重写旧文件（如把整个 Service 从字段注入改为构造器注入）
- 因编码风格不一致而在修改 bug 时顺便格式化整个文件
- 因缺少日志而在旧方法中逐行插入日志语句

### 3. 必须补齐被修改接口的文档注解

修改已有接口或新增接口时，必须为该接口补充缺失的文档注解：

需补充的注解（仅操作当前接口，不批量补充）：
- OpenAPI/Swagger 注解：`@Operation(summary=...)`、`@ApiResponse`、`@Parameter(description=...)`
- JavaDoc/JSDoc/Go Doc：方法功能说明、参数含义、返回值说明、异常说明
- 请求参数校验注解：`@NotNull`、`@NotBlank`、`@Valid` 等（如项目框架支持）

补充文档注解的价值：
- 为后续数字员工接入提供接口 Schema
- 不改变接口行为，零风险
- 降低新成员理解旧代码的成本

**不得仅因"旧代码没有注解"而跳过此规则**。skill 定义的"修改一个接口"是指修改行为本身附带补齐文档，而非先改行为再改文档。

### 4. 与 skill 冲突时的处理原则

当 skill 规则与旧项目代码风格冲突时，按以下优先级决策：

1. **安全相关规则不可妥协**：SQL 注入防范、密码加密、敏感信息脱敏 — 即使旧项目未实现，修改相关代码时必须补上
2. **结构相关规则可推迟**：分层架构、依赖注入方式、配置管理 — 仅在新建文件时应用，不在已有文件中强制改造
3. **风格相关规则需让步**：命名风格、注释格式、响应格式 — 沿用旧项目现有风格

## warn 级别软约束

- 分析旧项目代码风格后，向用户汇报检测到的风格模式（响应格式、错误码体系、命名惯例），并建议声明在 `./.super.yaml` 中固化
- 如果旧项目严重违反安全规则（明文密码、SQL 拼接），在修改相关代码时标注修复建议，但不强制在本次修改中全部修正
- 为新模块创建文件时，在文件头部添加注释说明该文件的代码风格依据（"沿用项目现有 DTO 命名风格"），避免未来维护者困惑为什么新旧文件风格一致但不完全符合 skill 规范
