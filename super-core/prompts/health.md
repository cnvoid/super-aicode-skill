# health — 健康检查规范

## error 级别硬约束

### 1. 所有服务必须暴露 /health 和 /ready 端点

每个后端服务必须暴露两个健康检查端点（不经过认证拦截器）：

- GET /health：存活探针，返回进程是否存活
- GET /ready：就绪探针，返回服务是否可接收请求

两个端点必须返回标准 HTTP 状态码，响应体为 JSON 格式。

### 2. /health 只检查进程存活

存活探针仅验证进程是否运行、是否未死锁。状态检查逻辑：
- 进程响应 HTTP 请求 → 200
- 进程无响应或崩溃 → 非 200

存活探针不得检查数据库、Redis 等外部依赖的连通性。存活探针失败意味着需要重启进程。

### 3. /ready 必须检查全部关键依赖

就绪探针必须逐一检查服务启动所需的全部关键依赖是否就绪：

- 数据库：尝试建立连接并执行简单查询
- Redis/缓存：尝试 PING 命令
- 消息队列：检查消费者/生产者连接状态
- 依赖的外部服务：发起一个轻量级请求确认连通性

任一关键依赖未就绪 → 返回 503，并在响应体中列出未就绪的组件及原因。就绪探针失败时，负载均衡和 K8s 不应将流量路由到该实例。

## warn 级别软约束

- 健康检查端点的响应体中包含各组件的状态详情（组件名、状态、延迟、错误信息），便于运维排查
- 就绪探针的请求间隔不超过 10 秒，检查超时不超过 5 秒，避免探针本身造成服务压力
- 在应用启动期间，就绪探针返回未就绪状态，直到所有初始化和预热操作完成
- 为就绪探针配置失败阈值（如连续 3 次失败判定为未就绪），防止因瞬时抖动误判
