# error — 异常处理规范

## error 级别硬约束

### 1. 所有 public 函数必须声明可能抛出的异常

函数的异常是其契约的一部分，必须在函数签名中显式声明。调用方无需阅读实现即可知道需要处理哪些异常。

各语言实现方式：
- Java: throws 子句声明 checked exception 或文档注释声明 unchecked exception
- Go: 返回 error 作为最后一个返回值
- TypeScript/JavaScript: JSDoc @throws 标签声明

不得仅在函数体内抛出异常而不在签名中声明。

### 2. 所有业务异常必须继承统一基类

项目必须定义一个顶层异常基类，所有业务异常继承自该基类。基类至少包含错误码和错误消息两个字段，构造函数支持传入 cause 异常以保留异常链。

全局异常处理器只需捕获该基类即可统一处理所有业务异常。

不得直接使用语言内置的通用异常类（如 RuntimeException、Error、通用 Exception）表示业务异常。

### 3. 不得吞异常

捕获异常后必须采取以下三种处理方式之一，不得空处理：

- 包装后重新抛出：将原始异常作为 cause 包装为业务异常后抛出
- 降级处理：执行备选逻辑后继续（需记录日志说明降级原因）
- 传播：直接重新抛出原始异常

以下行为属于吞异常，禁止：
- 空 catch 块
- catch 后仅打印日志不采取任何行动（除非该异常确属可忽略且已明确注释原因）
- catch 后仅 return null/default 而不记录日志

### 4. 错误码集中管理

所有业务错误码必须在统一的枚举或常量类中定义，按模块分组。错误码不允许散落在业务代码中硬编码。

错误码需包含：唯一标识、错误描述、对应的 HTTP 状态码（如适用）。

## warn 级别软约束

- 异常抛出时应记录结构化日志，包含 trace-id 和对入参的脱敏描述
- 对外部系统的调用需区分可重试异常和不可重试异常，分别定义不同的异常子类型
- 对外 API 的错误响应使用统一结构：code、message、traceId
