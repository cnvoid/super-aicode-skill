# ai-testing — AI 测试规范

## error 级别硬约束

### 1. AI 生成代码必须通过专项检查

AI 生成的代码在合入前，必须通过以下三项专项检查（传统测试之外）：

**幻觉检测**：检查代码中是否调用了不存在的函数、类、方法、库。检测方法：
- 静态分析：验证所有 import/require 的模块是否在 package.json/go.mod/pom.xml 中声明
- 编译验证：确保代码能成功编译/构建，无未解析的引用
- API 存在性：验证调用的第三方库 API 是否确实存在（版本匹配）

**冗余模式检测**：检查 AI 是否在输出中出现了机械重复的模式：
- 连续多个完全相同结构的代码块（仅变量名不同）
- 多个同类函数中相同的参数列表和返回值结构（应抽象为泛型或接口）
- 测试用例中连续的、无意义的参数变更（应使用参数化测试）

**规则遵循度验证**：验证 AI 是否真的遵守了 skill 约束：
- 检查是否使用 Optional Chaining（`?.`）而非裸属性访问
- 检查异常是否继承 BaseException 而非直接抛 RuntimeException
- 检查日志是否使用结构化格式而非字符串拼接
- 检查响应体是否包裹在 `{code, message, data}` 中

每项检查不通过时，必须标记具体文件、行号和违反的规则，要求 AI 或开发者修正。

### 2. AI 辅助生成测试用例：必须人工 Review

AI 可用于辅助生成测试用例，但必须遵循以下流程：

生成阶段（AI 执行）：
- 读取目标源代码，识别所有 public 函数和分支路径
- 为每个函数生成正向/边界/异常三类测试骨架
- 生成符合业务领域规则的测试数据

审查阶段（人工或工具执行）：
- 验证每个测试用例的 then 断言是否正确（AI 容易生成"伪断言"：assertNotNull 替代具体断言）
- 验证 Mock 对象的行为是否与实际依赖一致（AI 编造的 mock 行为可能与真实实现矛盾）
- 验证边界值是否覆盖了业务文档而非仅覆盖代码中的 if 条件
- 验证异常场景的异常类型和错误码与实际一致

禁止行为：
- 不经审查直接合并 AI 生成的测试用例
- 仅凭 AI 生成的测试通过即认为代码合格
- 用 AI 测试覆盖率的数值代替人工对测试质量的判断

### 3. Skill 包自验证：确保约束真正生效

技能包本身必须通过自验证，确保其约束能够真正影响 Agent 的输出：

**Golden 测试**：
- 准备 5-10 组标准输入（如"写一个创建订单的接口"）
- 记录在不加载 skill 时 Agent 的输出（基线）
- 记录在加载 skill 后 Agent 的输出
- 对比两者差异，量化验证 skill 的影响效果

**逐条开关验证**：
- 关闭所有规则 → 验证 Agent 输出自由、无约束
- 逐条打开 error 级规则 → 验证 Agent 输出中确实包含了对应约束
- 将规则从 error 改为 warn → 验证 Agent 输出从硬拒绝变为软提示

**对抗测试**：
- 故意要求 Agent "不写测试"、"不使用 Optional Chaining"、"直接返回裸数据"
- 验证 Agent 是否拒绝了该要求，并给出了规则依据
- 验证 Agent 在被迫放弃约束时是否标注了原因

**跨模型一致性**：
- 同一 skill 在不同模型下（Claude、GPT、DeepSeek）执行相同的 Golden 输入
- 验证输出是否满足相同的规则约束
- 发现某些模型系统性忽略某条规则时，调整 prompt 措辞以增强约束力

## warn 级别软约束

- AI 测试生成的用例数量和覆盖率作为参考指标，不作为质量门禁
- 定期更新 Golden 测试输入集，覆盖新增的规则和场景
- 对抗测试的结果用于持续优化 prompt 中规则的表述方式
