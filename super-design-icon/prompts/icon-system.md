# icon-system — 图标系统架构规范

## error 级别硬约束

### 1. 图标目录必须按功能分组

图标组件库的目录结构必须清晰，按功能或业务领域分组。推荐结构：

```
icons/
├── index.ts                    # 统一导出入口，re-export 所有图标
├── types.ts                    # 图标 Props 类型定义 + IconName 联合类型
├── common/                     # 通用图标（箭头、关闭、搜索等）
│   ├── ArrowLeft.tsx
│   ├── Close.tsx
│   └── Search.tsx
├── navigation/                 # 导航图标
├── action/                     # 操作图标（编辑、删除、添加）
├── status/                     # 状态图标（成功、失败、警告、信息）
├── file/                       # 文件类型图标
└── brand/                      # 品牌/Logo 图标
```

不得将所有图标平铺在单一目录中。

### 2. 必须支持 tree-shaking

图标库的导出结构必须支持打包工具的 tree-shaking，确保使用者导入单个图标时只打包该图标对应的代码，不会加载全部图标资源。

实现方案（按优先级）：
- 每个图标独立的具名导出，配合使用方的具名导入实现 tree-shaking
- 在 package.json 中配置 sideEffects: false 声明无副作用
- 提供独立的子路径导出（如 @lib/icons/ArrowLeft）

禁止使用单一 default export 对象包含全部图标的写法，该方式会导致 tree-shaking 失效。

### 3. 必须导出统一的类型定义

图标组件库必须导出一个 IconName 联合类型，包含所有可用图标的名称字面量。使用方通过该类型获得图标名称的 IDE 自动补全和编译期校验。

## warn 级别软约束

- 图标组件库发布为独立 npm 包时，提供 ESM 和 CJS 双格式输出
- 文档中提供所有图标的在线预览页面（可通过 Storybook 或自定义页面实现）
- 图标源码（SVG 文件）保留在仓库中，组件由构建脚本自动生成，避免手工维护组件的同步问题
- 构建流程集成 SVGO 优化和尺寸校验，在 CI 中拦截不合规的 SVG

### 4. 按需加载策略建议

图标库的引用方式优先级：
- 直接导入单个图标组件（推荐，静态分析友好）
- 通过统一入口的具名导入（需确保 tree-shaking 生效）
- 通过 Iconify 等图标框架的动态加载（运行时按需）
- 全局注册所有图标（不推荐，仅适用图标数量极少且全部需要的场景）
